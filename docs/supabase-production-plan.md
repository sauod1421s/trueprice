## الطريقة: ملف واحد في SQL Editor

بدل تقسيم الملفات وتمريرها عبر الموصل (الذي يرفض الملفات الكبيرة وأوامر `drop` المتضمنة في السياسات)،
الملف `db/supabase/setup_all.sql` يُلصق **مرة واحدة** في **SQL Editor** داخل لوحة Supabase ويُضغط **Run**.

الملف مولَّد آليًا (`npm run db:setup-all`) من ملفات الإنتاج نفسها **حرفيًا** وبالترتيب، و CI يرفض أي فرق
(`npm run db:setup-all:check`). كل ملف داخله يحتفظ بمعاملته (`begin … commit`): أي خطأ يلغي الملف كله.

| # | المحتوى | ملاحظات |
| --- | --- | --- |
| 0 | فحص مسبق (لا يغيّر شيئًا) | يتوقف فورًا إن لم يكن في Authentication مستخدم أو مستخدمان بالضبط |
| 1 | `db/schema/001_trueprice_v1_1.sql` | المخطط، الأدوار، RLS على كل جدول، دوال الاستيراد والمراجعة، سجل التدقيق |
| 2 | `db/mvp/002_mvp_overlay.sql` | واجهات الموقع ودوال اللوحة، والتعطيل المؤقت القابل للعكس (الريال فقط، لا استيراد آلي، حد 1,000 صف) |
| 3 | `db/schema/003_visitors_requests.sql` | إحصائيات الزوار بلا تخزين IP، طلبات التواصل والشكاوى بالرقم المرجعي ورمز المتابعة، إعدادات التواصل |

## ما تم التحقق منه قبل التسليم (محليًا، PostgreSQL 17، دور ترحيل غير مدير يحاكي `postgres` في Supabase)

`npm run db:setup-all:verify` (يعمل في CI أيضًا) — 28 فحصًا ناجحًا:

- بلا مستخدمين أو بثلاثة: يتوقف برسالة عربية واضحة **قبل أي تغيير** (لا يُنشأ أي مخطط).
- بمستخدم واحد أو اثنين: ينجح في نحو ثانيتين؛ 0 مخالفات صلاحيات؛ الأعداد مطابقة؛ لا سعر قديم يظهر كمعتمد؛
  كل مشرف منحه الآخر (لا منح ذاتي)؛ كلمة المرور المعروضة تعمل فعلًا.
- إعادة التشغيل: لا تكرر شيئًا، وتدوّر كلمة المرور (القديمة تتوقف).
- البنية بعد التشغيل مرتين مطابقة تمامًا لتطبيق الملفات منفصلة (378 عنصرًا: جداول ودوال وصلاحيات وسياسات).
- ملف التراجع: يرفض بلا تأكيد، ويحذف كل شيء عند التأكيد دون مس `auth.users`، ثم ينجح الإعداد من جديد.

**لم يُختبر على Supabase الحقيقي بعد** (بيئة العمل لا تصل إلى `supabase.co`)، لذلك نتيجة الفحوص في الصف الأخير
إلزامية القراءة، وبعد التنفيذ أتحقق بنفسي عبر موصل Supabase (قراءة فقط).

## تحذيرات SQL Editor المتوقعة (مراجَعة سطرًا سطرًا — أرقام الأسطر في setup_all.sql)

يفحص Supabase Studio النص بأنماط نصية بسيطة قبل التشغيل، فتظهر ثلاثة تحذيرات. كلها مقصودة وآمنة على مشروع جديد:

| التحذير | الأسطر | السبب الفعلي | الأثر على مشروع فارغ |
| --- | --- | --- | --- |
| عمليات مدمرة | 2164، 2600، 2603، 2606، 2610 | `drop trigger/policy if exists` على جداول ينشئها الملف نفسه ثم يعيد إنشاء العنصر فورًا (إعادة تشغيل آمنة) | لا شيء: العنصر غير موجود بعد |
| عمليات مدمرة | 2309 (حلقة 2307–2310) | `drop policy` لسياسات مخطط `tp` الموجودة فقط قبل إعادة إنشائها | لا شيء: لا سياسات بعد |
| عمليات مدمرة | 2490، 2491 | `drop policy if exists` لسياستينا فقط على `storage.objects` (حاوية `imports` الخاصة) ثم إنشاؤهما | لا شيء: 0 سياسات و0 حاويات حاليًا (فُحص) |
| عمليات مدمرة | 1478، 1929، 1932، 1938، 2053، 2807، 2817، 2827، 2983 | `delete`/`truncate` داخل دوال لا تعمل إلا عند استدعائها: جدول عمل مؤقت للاستيراد، مهمة الاحتفاظ، سحب دور، تنظيف ملح الزوار وحدود المعدل، مسح إعداد | لا شيء عند الإعداد (الملف لا يستدعي هذه الدوال، عدا جدول العمل المؤقت أدناه) |
| UPDATE بلا WHERE | 1584 | داخل `tp.commit_import_core` (1422): تصنيف كل صفوف جدول العمل المؤقت `pg_temp.tp_apply` (أُنشئ في 1460 `on commit drop`) — مقصود لكل الصفوف | يمس جدولًا مؤقتًا خاصًا بالجلسة فقط |
| جداول بلا RLS (42) | إنشاء الجداول 166–797 | RLS يُفعَّل لها كلها بحلقة ديناميكية في 2304–2306 (`execute format('alter table tp.%I enable row level security')`) لا يراها الفاحص النصي. جداول 002/003 السبعة لها أوامر صريحة (2598، 2778، 2786، 2850، 2950، 3012، 3023) فلا تظهر | لا نافذة بلا حماية: الإنشاء والتفعيل في معاملة 001 نفسها. عمود `privilege_violations_expect_0` في النتيجة يتضمن فحص «جدول بلا RLS» (1163–1166) |

**القرار:** اضغط **Run without RLS** — الاسم مضلل هنا؛ معناه «شغّل الملف كما هو دون أن يُلحق Supabase أوامر». لا تضغط
**Run and enable RLS**: يُلحق 42 أمر `ALTER TABLE … ENABLE ROW LEVEL SECURITY` في آخر النص، وهي بلا أثر (RLS مفعّل
أصلًا — مُختبر: البنية والصلاحيات مطابقة تمامًا)، لكنها تصبح آخر أمر فلا يظهر صف `database_url`.

تحقق `npm run db:setup-all:verify` من: RLS على 49/49 جدولًا، ولا صلاحية لـ anon/public/service_role، ومحاكاة زر
«Run and enable RLS» (نجاح بلا تغيير، واختفاء صف النتيجة). وفي مشروع Supabase نفسه (قراءة فقط): `postgres` مسموح له
بإدارة سياسات `storage.objects` (`supautils.policy_grants`)، ويملك خيار الإدارة على `authenticated` الذي يحتاجه 010.

## إعادة التشغيل والتراجع

- إعادة تشغيل `setup_all.sql` آمنة، لكنها تولّد كلمة مرور جديدة لـ `tp_app` (يجب تحديث `DATABASE_URL` في Vercel).
- التراجع الكامل: `db/supabase/rollback_all.sql` — حذف نهائي، **بموافقة صريحة فقط**، محمي بسطر تأكيد. التفاصيل
  في `docs/rollback-and-launch-ar.md`.

## مخاطر يجب معرفتها

- **الخطة المجانية:** يتوقف المشروع بعد 7 أيام بلا نشاط (يُستأنف من اللوحة)، ولا نسخ احتياطية تلقائية، والحد 500 م.ب.
- **`DATABASE_URL` بحساسية `service_role`:** متغير خادم فقط على Vercel، لا يبدأ بـ `NEXT_PUBLIC_`، ولا يُرسل في أي رسالة.
- **تحقق TLS كامل دائمًا:** شهادات Supabase الجذرية العامة مضمّنة (من مستودع Supabase الرسمي) وتُضاف لجذور النظام؛
  لا اتصال بلا تحقق من هوية الخادم.
