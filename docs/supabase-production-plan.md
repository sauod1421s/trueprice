- الفرع المصدر: `mvp-live-preview` فقط. لا تعديل على `main` ولا على الموقع الرسمي ولا DNS.

## الطريقة: ملف واحد في SQL Editor

بدل تقسيم الملفات وتمريرها عبر الموصل (الذي يرفض الملفات الكبيرة وأوامر `drop` المتضمنة في السياسات)،
الملف `db/supabase/setup_all.sql` يُلصق **مرة واحدة** في **SQL Editor** داخل لوحة Supabase ويُضغط **Run**.

الملف مولَّد آليًا (`npm run db:setup-all`) من ملفات الإنتاج نفسها **حرفيًا** وبالترتيب، و CI يرفض أي فرق
(`npm run db:setup-all:check`). كل ملف داخله يحتفظ بمعاملته (`begin … commit`): أي خطأ يلغي الملف كله.

| # | المحتوى | ملاحظات |
| --- | --- | --- |
| 0 | فحص مسبق (لا يغيّر شيئًا) | يتوقف فورًا إن لم يكن في Authentication مستخدم أو مستخدمان بالضبط |
| 1 | `db/schema/001_trueprice_v1_1.sql` | المخطط، الأدوار، RLS على كل جدول، دوال الاستيراد والمراجعة، سجل التدقيق |
| 2 | `db/mvp/002_mvp_overlay.sql` | واجهات الموقع ودوال اللوحة، والتعطيل المؤقت القابل للعكس (الريال فقط، لا استيراد آلي، حد 1,000 صف) |
| 3 | `db/schema/003_visitors_requests.sql` | إحصائيات الزوار بلا تخزين IP، طلبات التواصل والشكاوى بالرقم المرجعي ورمز المتابعة، إعدادات التواصل |
| 4 | `db/supabase/010_app_role.sql` | دور اتصال الموقع `tp_app` (لا صلاحيات بنفسه، يتحول إلى `web_reader` أو `authenticated`) |
| 5 | تهيئة المشرفين | من مستخدمي Authentication الموجودين (1 أو 2)، مرة واحدة ثم تُقفل الدالة نفسها |
| 6 | `db/seed/100_catalog_seed.sql` | 52 منتجًا إلكترونيًا + 357 سيارة + 283 سعرًا مرجعيًا — كلها **غير موثقة** ولا تدخل السعر العادل |
| 7 | دالة `020_set_app_password.sql` + الفحوص | تولّد كلمة مرور `tp_app` داخل القاعدة وتعرض رابط `DATABASE_URL` مرة واحدة مع نتيجة الفحوص |

## ما تم التحقق منه قبل التسليم (محليًا، PostgreSQL 17، دور ترحيل غير مدير يحاكي `postgres` في Supabase)

`npm run db:setup-all:verify` (يعمل في CI أيضًا) — 28 فحصًا ناجحًا:

- بلا مستخدمين أو بثلاثة: يتوقف برسالة عربية واضحة **قبل أي تغيير** (لا يُنشأ أي مخطط).
- بمستخدم واحد أو اثنين: ينجح في نحو ثانيتين؛ 0 مخالفات صلاحيات؛ الأعداد مطابقة؛ لا سعر قديم يظهر كمعتمد؛
  كل مشرف منحه الآخر (لا منح ذاتي)؛ كلمة المرور المعروضة تعمل فعلًا.
- إعادة التشغيل: لا تكرر شيئًا، وتدوّر كلمة المرور (القديمة تتوقف).
- البنية بعد التشغيل مرتين مطابقة تمامًا لتطبيق الملفات منفصلة (378 عنصرًا: جداول ودوال وصلاحيات وسياسات).
- ملف التراجع: يرفض بلا تأكيد، ويحذف كل شيء عند التأكيد دون مس `auth.users`، ثم ينجح الإعداد من جديد.

**لم يُختبر على Supabase الحقيقي بعد** (بيئة العمل لا تصل إلى `supabase.co`)، لذلك نتيجة الفحوص في الصف الأخير
إلزامية القراءة، وبعد التنفيذ أتحقق بنفسي عبر موصل Supabase (قراءة فقط).

## عن كلمات drop/delete داخل الملف

لا أمر يحذف بيانات قائمة. الكلمات الموجودة هي: إعادة إنشاء سياسات RLS بأسمائها (`drop policy if exists` ثم
`create policy`)، أو داخل دوال لا تعمل إلا عند استدعائها، أو مشغلات تمنع الحذف من جداول السجل. قد تعرض لوحة
Supabase تنبيه «عملية قد تكون مدمرة» بسببها؛ التأكيد آمن هنا.

## إعادة التشغيل والتراجع

- إعادة تشغيل `setup_all.sql` آمنة، لكنها تولّد كلمة مرور جديدة لـ `tp_app` (يجب تحديث `DATABASE_URL` في Vercel).
- التراجع الكامل: `db/supabase/rollback_all.sql` — حذف نهائي، **بموافقة صريحة فقط**، محمي بسطر تأكيد. التفاصيل
  في `docs/rollback-and-launch-ar.md`.

## مخاطر يجب معرفتها

- **الخطة المجانية:** يتوقف المشروع بعد 7 أيام بلا نشاط (يُستأنف من اللوحة)، ولا نسخ احتياطية تلقائية، والحد 500 م.ب.
- **`DATABASE_URL` بحساسية `service_role`:** متغير خادم فقط على Vercel، لا يبدأ بـ `NEXT_PUBLIC_`، ولا يُرسل في أي رسالة.
- **شهادة SSL إلزامية:** بدون `DATABASE_CA_CERT` يرفض الموقع الاتصال (مقصود: لا اتصال بلا تحقق من هوية الخادم).
