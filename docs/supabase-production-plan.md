# خطة تنفيذ قاعدة TruePrice على Supabase (`trueprice-production`) — بانتظار الموافقة

> **الحالة: لم يُنفَّذ أي شيء على Supabase.** هذه الخطة للمراجعة. لا يُشغَّل أي ملف قبل موافقة صريحة
> من صاحب المشروع على هذه الخطة نفسها.

- المشروع: `trueprice-production` — المنطقة Frankfurt (`eu-central-1`) — الخطة المجانية (Free).
- الفرع المصدر: `mvp-live-preview` (لا تعديل على `main`، ولا نشر على Vercel ضمن هذه الخطة).
- كل الملفات **إضافية وقابلة للإعادة**: لا تحذف أي بيانات، ولا تعيد ضبط القاعدة، ولا تمس جداول Supabase
  الأصلية (`auth.*`). تشغيل أي ملف مرتين لا يكرر شيئًا.

## ما تم التحقق منه قبل الخطة

| الفحص | النتيجة |
| --- | --- |
| تطبيق كل الملفات بالترتيب على PostgreSQL 17 محلي بدور ترحيل **غير مدير** يحاكي `postgres` في Supabase | نجح، وإعادة التشغيل لا تكرر شيئًا |
| فاحص الصلاحيات `tp.privilege_violations()` بعد التطبيق | 0 مخالفة |
| نقل البيانات | 52 منتجًا إلكترونيًا + 357 سيارة + 283 سعرًا مرجعيًا (208 إلكترونيات + 75 سيارات) |
| الأسعار المرجعية القديمة | مصدر `legacy_manual`: غير موثقة + تاريخ غير مؤكد → **لا تدخل السعر العادل ولا تظهر كسعر معتمد** |
| روابط `/product/[id]` الحالية | محفوظة عبر `legacy_id` |
| قواعد القاعدة (اختبارات آلية على القاعدة المحلية) | 10/10 (منع القراءة العامة للجداول الخاصة، الريال فقط، منع المراجعة الذاتية، المصدر الموقوف لا يقبل استيرادًا، ...) |

**لم يُختبر بعد على Supabase الحقيقي** (الشبكة من بيئة العمل لا تصل إلى `supabase.co`): هذه أول مرة
ستُطبَّق فيها الملفات على Supabase نفسه، لذلك الخطوة 0 (نسخة احتياطية) والخطوة 2 (فحص بعد كل ملف) إلزاميتان.

## الترتيب المقترح

كل خطوة تُنفَّذ في **SQL Editor** داخل لوحة Supabase (أو عبر موصل Supabase بعد ربطه، فأنفذها أنا وأعرض
النتيجة). كل ملف داخل معاملة واحدة (`begin … commit`): إذا فشل أي سطر لا يُطبَّق شيء من الملف.

| # | الملف | ماذا يفعل | متى |
| --- | --- | --- | --- |
| 0 | — | تأكيد أن المشروع جديد وفارغ (لا جداول في المخطط `tp`)، وأخذ نسخة يدوية إن وُجدت بيانات | قبل البدء |
| 1 | `db/schema/001_trueprice_v1_1.sql` | المخطط v1.1.1: المخططات `tp` و`pub` و`admin_api` و`ingest_api`، الأدوار `tp_owner` و`web_reader` و`ingest_service`، RLS على كل جدول، دوال الاستيراد والمراجعة، سجل التدقيق | الآن (بعد الموافقة) |
| 2 | `db/mvp/002_mvp_overlay.sql` | واجهات الموقع (`pub.product_details`، `pub.price_history`)، دوال اللوحة (الملف الشخصي، المستخدمون)، والتعطيل المؤقت القابل للعكس: الريال فقط، لا تحويل عملات، لا استيراد آلي، حد 1,000 صف | الآن |
| 3 | `db/supabase/010_app_role.sql` | دور اتصال الموقع `tp_app` (بلا كلمة مرور بعد): يتصل ثم يتقمص `web_reader` للموقع العام أو `authenticated` للوحة، مع مهلات قصيرة | الآن |
| 4 | — | إنشاء أول مشرفَين في Supabase Auth من اللوحة (انظر دليل الإعداد) ونسخ معرّفيهما (UUID) | الآن (يدويًا من صاحب المشروع) |
| 5 | `select tp.bootstrap_first_admins('<UUID-1>', '<الاسم 1>', '<UUID-2>', '<الاسم 2>');` | تهيئة أول مشرفَين — تعمل **مرة واحدة فقط** ثم تُقفل نفسها | الآن |
| 6 | `db/seed/100_catalog_seed.sql` | نقل الكتالوج والسيارات والأسعار المرجعية عبر مسار الاستيراد الرسمي نفسه (تسجيل → رفع → ختم SHA-256 → تطبيق)، باسم المشرف الأول | الآن |
| 7 | `db/supabase/020_set_app_password.sql` | يولّد كلمة مرور عشوائية لـ `tp_app` ويعرضها **مرة واحدة** لتوضع في `DATABASE_URL` على Vercel | **عند الإطلاق فقط** (لا داعي لكلمة مرور لا تُستخدم) |

### فحوص بعد كل خطوة (قراءة فقط)

```sql
-- بعد 1 و2 و3: يجب أن تكون النتيجة صفرًا
select count(*) from tp.privilege_violations();
select version from tp.schema_migrations order by applied_at;      -- v1.1, v1.1.1, mvp-overlay-1, mvp-overlay-2

-- بعد 5
select * from tp.bootstrap_state;                                   -- صف واحد بمعرّفي المشرفَين

-- بعد 6
select category_kind, count(*) from tp.products group by 1;         -- electronics 52 · cars 357
select source_id, count(*) from tp.price_observations group by 1;   -- legacy-site-data 208 · legacy-site-cars 75
select count(*) from pub.electronics_offers;                        -- 0: لا سعر قديم يظهر كمعتمد
select count(*) from tp.verification_events;                        -- 0: لم يُوثَّق شيء آليًا
```

### عن أوامر الحذف التي قد تظهر داخل الملفات

لا يوجد في أي ملف أمر يحذف بيانات عند التنفيذ. الكلمات `delete`/`truncate`/`drop` الموجودة هي:
داخل دوال لا تعمل إلا عند استدعائها (تنظيف الملاحظات المؤقتة بعد مدة الاحتفاظ، وسحب دور)، أو جدول مؤقت
داخل الجلسة، أو إعادة إنشاء سياسات RLS بأسمائها (`drop policy if exists` ثم `create policy`)،
أو مشغلات تمنع الحذف أصلًا من جداول السجل.

## ما يحتاج تدخل صاحب المشروع

1. **الموافقة على هذه الخطة** (أو طلب تعديلها).
2. **أحد طريقين للتنفيذ:**
   - ربط موصل Supabase بهذه المحادثة، فأنفذ الخطوات 1–3 و5–6 وأعرض نتيجة كل فحص قبل الانتقال للتالي؛ أو
   - نسخ محتوى كل ملف ولصقه في SQL Editor بالترتيب (أرسل لك الملفات جاهزة).
3. **إنشاء المستخدمين** في Authentication → Users (لا أنشئ حسابات نيابة عنك).
4. إعدادات الأمان في لوحة Supabase الواردة في `docs/supabase-setup-ar.md`.

## التراجع

- قبل الخطوة 6 لا توجد بيانات حقيقية؛ المشروع مجاني وجديد، فالتراجع الأبسط هو مشروع Supabase جديد.
- بعد الخطوة 6: البيانات المنقولة نسخة من ملفات الموقع الحالية (ما زالت في Git)، فلا يضيع شيء.
- الموقع الرسمي الحالي لا يتأثر بأي خطوة هنا: يعمل من ملفات `app/data` (الوضع `static`) حتى يُضبط
  `TP_DATA_SOURCE=db` على Vercel، وهذا خارج هذه الخطة.

## مخاطر يجب معرفتها قبل الإطلاق

- **الخطة المجانية:** المشروع يتوقف تلقائيًا بعد 7 أيام بلا نشاط، ولا توجد نسخ احتياطية تلقائية، والحد 500 م.ب.
  للبيانات. مناسبة للتجربة؛ للإطلاق الرسمي يلزم نسخ احتياطي يدوي دوري أو ترقية (قرارك، لن أشترك في أي خطة).
- **`DATABASE_URL` بحساسية `service_role`:** دور `tp_app` يستطيع تقمص أي مستخدم داخل القاعدة. يوضع فقط في
  متغيرات الخادم على Vercel، ولا يبدأ أبدًا بـ `NEXT_PUBLIC_`.
- **شهادة SSL:** الاتصال يرفض أي خادم لا يطابق شهادة Supabase (`DATABASE_CA_CERT`) — بدونها لا يعمل الموقع
  بوضع القاعدة، وهذا مقصود.
- **أول تطبيق على Supabase الحقيقي:** فروق بيئية محتملة (إصدار PostgreSQL، صلاحيات `postgres`) لم تظهر في
  المحاكاة المحلية. الفحوص أعلاه تكشفها مبكرًا، وكل ملف يُلغى بالكامل عند أي خطأ.
